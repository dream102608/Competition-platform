### V3.3 演示模式升级：CSV 模态 → 真 .xlsx 一键打开
- **再次问题**：用户反馈"为什么是这种形式而不是 Excel 表格"——前一次 demoExport 只给 CSV modal 预览，但 WeChat `openDocument` 不支持 CSV（只接 doc/docx/xls/xlsx/ppt/pptx/pdf 7 种）。
- **解决方法**：在 `utils/data.js` 末尾加 `packXlsx(sheetName, rows)`，纯手写 OOXML + zip。
  - `Uint8Array + DataView` 直接搓 ZIP STORE 格式（30B local file header + 46B central directory + 22B EOCD），无 `pako/jszip/fflate` 等任何依赖
  - 表驱动 CRC32（256 项，多项式 `0xEDB88320`，与 zlib 输出一致）
  - 5 个内嵌 XML：`[Content_Types].xml` / `_rels/.rels` / `xl/workbook.xml` / `xl/_rels/workbook.xml.rels` / `xl/worksheets/sheet1.xml`
  - 字符串走 `<is><t xml:space="preserve">` inlineStr，数字走 `<v>`
  - UTF-8 编码优先 `TextEncoder`，旧设备有手工 fallback
  - 中文字段 _esc 转义处理 `& < > "`，避免列名/数据中的特殊字符破坏 XML
- **接入**：`demoExport()` 现同步 `writeFileSync(bytes.buffer, 'binary')` 到 `wx.env.USER_DATA_PATH/<title>_<date>.xlsx`；`openXlsx()` 检测本地路径直接 `wx.openDocument({ filePath, fileType:'xlsx', showMenu:true })` 打开，右上角可转发/保存/收藏。
- **降级**：xlsx 写失败（旧设备 / 权限）→ 返回 `fileID='__demo_csv__'` → `openXlsx` reject → `_showDemoPreview` 弹 CSV modal 兜底，保证功能不卡死。
- **8 个 kind 端到端校验**：用 Node 抽 packXlsx 跑全部 kind 生成 .xlsx，再用 Python `zipfile` + 正则解析 sheet1.xml：
  - regs（报名名单）：3432B / 16 cells / 14 中文
  - oneCompRegs（单个竞赛）：4065B / 24 cells / 20 中文
  - myAdvisees（指导学生）：2829B / 6 cells / 6 中文
  - studentAwards（获奖名单）：3282B / 14 cells / 13 中文
  - trainingSignups（培训记录）：3140B / 12 cells / 10 中文
  - free（空闲学生）：2819B / 8 cells / 8 中文
  - expenses（经费台账）：3057B / 11 cells / 10 中文
  - schedules（课表明细）：3183B / 13 cells / 11 中文
  - **全部 5 个 OOXML entry 齐全 + sheet1.xml 解析 + 中文字段无损坏**
- **为什么不用 STORED 之外的压缩**：单 sheet + 几十/几百行文本 压缩后更小但增加复杂度，对 1-10KB 规模收益不大；存 STORE 调试更友好（unzip 直接看到原始 XML）。

### V3.3 第 2 次踩坑：用户截到「单竞赛明细」走 CSV modal
- **现象**：用户截到 demoExport `__demo_csv__` 兜底弹窗，不是预想中的 .xlsx。
- **根因排查**：
  1. 第一次写文件用 `bytes.buffer.slice(..., 'binary')` —— WeChat `writeFileSync` 在 iOS 上对 ArrayBuffer + binary encoding 的解释有歧义，AAR/Instance 实现不一致
  2. 用户大概率没重启微信开发者工具，所以看到的还是旧版 demoExport
- **修复**（已写入 data.js）：
  1. **`_b64encode(Uint8Array) → string`**：手写 50 行 base64 编码（无依赖、零开销），把 Uint8Array 先编码成纯字符串。
  2. **`fm.writeFileSync(xlsxPath, _b64encode(bytes), 'base64')`**：绕开 ArrayBuffer 处理歧义，是 WeChat 写二进制最稳的姿势。
  3. **路径 fallback**：`baseDir = wx.env.USER_DATA_PATH || '/tmp'`，配合 `fm.unlinkSync` 先删后写。
  4. **catch 块记详细错误**：`xlsxErr = e.message || e.errMsg`，写进 modal 给用户看为什么失败。
  5. **openXlsx 加重试**：失败时去掉 `fileType: 'xlsx'` 再试 `openDocument`（让 WeChat 自动嗅探 mime）。
- **端到端二次校验**：
  1. Python 脚本精确截取 data.js 中的 `packXlsx` 函数（AST 嵌套计数），导出为 `module.exports = { packXlsx }`
  2. Node 跑 8 种 kind，写出 8 个真实 xlsx（3.0-4.0KB）
  3. Python `zipfile.ZipFile` 解每个 xlsx，看 `infolist()` 的 header_offset：
     - `[Content_Types].xml` @ 0
     - `_rels/.rels` @ 606
     - `xl/workbook.xml` @ 942
     - `xl/_rels/workbook.xml.rels` @ 1276~1282
     - `xl/worksheets/sheet1.xml` @ 1628~1634
  4. 每个 sheet1.xml 正则解析 cells：8~24 中文 cells，全部正确
- **结论**：packXlsx 本身没问题，结构正确；变动只在写盘姿势（base64 更稳）。
- **交付**：按用户要求把 V3.3.1 涉及的全部 11 个源文件打包为 `D:/Jing/jingsai-v1-data-export-V3.3.1.zip`（保留相对 jingsai-v1/ 目录结构，45.4 KB / 149.6 KB 解压），用户可直接下载并覆盖回项目根目录。

### V3.3.1 patch · 演示模式多路径写盘兜底 + Console 诊断
- **再现象**：base64 写完后，部分设备仍走 CSV 兜底 modal。需要知道到底哪一步失败。
- **新策略**：不假定 USER_DATA_PATH 一定能用，写盘函数 `_writeDemoXlsx(fileName, bytes)` 一次试三条路径：
  1. `USER_DATA_PATH/<file>.xlsx`
  2. `USER_DATA_PATH/tmp/<file>.xlsx`
  3. `/tmp/<file>.xlsx`
  每条路径都 `mkdirSync(dir, true)` 建目录 → `unlinkSync` 先删旧 → `writeFileSync` → `statSync` 校验 size ≥ bytes.length - 32。任一条成功立即返回，所有失败才回 `__demo_csv__`。
- **诊断**：每个分支都 `console.log/warn/error` 输出 `[demoExport]` / `[openXlsx]` 日志，开发者工具 Console 一眼能看到「写入成功: <路径> · 字节: <N>」或「写盘失败: <err>」，定位无需靠用户描述。
- **失败提示升级**：`pages/export/export.js _showDemoPreview` 把 `xlsxErr` 摆在 modal 最前（`⚠️ xlsx 写盘失败：…`），并提示「开发者工具 Console 有详细日志」。
